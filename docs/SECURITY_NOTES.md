# FindBack 2.0 security notes

**Release status:** Phases 1–7 are implemented with targeted local tests, including disposable PostgreSQL/RLS checks and a Chrome Demo workflow. No live Supabase verification, deployment or FINAL AUDIT has been performed. Local tests use stand-in Auth/Storage schemas and do not prove production security.

- Demo mode uses browser-local sample data. It is for testing only and is not secure or multi-user.
- Cloud mode uses local environment settings or the host's environment variables. The browser receives only the Supabase Project URL and publishable key. Never use a service-role/secret key in browser code or `NEXT_PUBLIC_*`. A publishable key is preferred; a legacy JWT with the `anon` role is accepted. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).
- Production Cloud configuration requires an explicit `APP_ORIGIN` HTTPS origin, used for Auth redirects. URL credentials, paths, queries and fragments are rejected. Development permits HTTP loopback origins. Production validation rejects malformed configuration and public variables named as secrets; it does not verify credential validity, connectivity or migrations. Keep deployment values explicit and run `npm run release:check -- --mode cloud` before release.
- Confirmation/callback routes validate token type/shape, catch exchange failures, use fixed redirect destinations and show fixed feedback without reflecting supplied errors or `next` URLs. Demo mode never exchanges Auth tokens. Recovery routes return only to the password-reset page. Auth responses are private/no-store with no-referrer.
- The Cloud proxy copies the cookie/cache headers supplied by Supabase SSR and adds private/no-store plus `Vary: Cookie` on app responses. Hosts/CDNs must honor these headers; verify this on the deployed domain. Do not add public caching to authenticated responses. [Supabase SSR caching guidance](https://supabase.com/docs/guides/auth/server-side/advanced-guide).
- HTTP responses include CSP, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a restricted Permissions-Policy and Referrer-Policy. Production adds HSTS and HTTPS upgrades. CSP allows the configured Supabase HTTPS/WebSocket origin, local development sockets and local/data/blob images. Inline scripts/styles remain allowed for Next.js hydration and existing styles; development also permits eval. This policy does not eliminate inline-XSS risk. [Next.js CSP guidance](https://nextjs.org/docs/app/guides/content-security-policy).
- The database enforces the `@seu.edu.bd` domain during Auth user creation and email updates. Keep email confirmation enabled.
- Admin roles come from `admin_members`, not browser state or editable profile metadata. Provision admins only through trusted database-owner access.
- Visible report fields and ordinary item photos are public. Contact phone numbers, profile emails, claims, messages, notifications, flags and audit records use role/participant-specific RLS.
- Report and claim state changes use PostgreSQL functions that validate the authenticated user, ownership and allowed transition.
- Suspended accounts are blocked from private reads, storage operations and application writes by `is_active_member()` checks.
- The `report-images` bucket is public. The UI and Step 3 database constraint block photos for the `ID Card` category. Never upload student cards, national IDs, QR codes, passwords, financial information or private documents under any category.
- The report form compresses accepted JPG/PNG/WebP images in the browser before upload. Public image content remains public after compression.
- Replaced or cleared report images are removed from Storage after the database update. Storage cleanup is best-effort; verify Storage after testing.
- Both claim participants must separately confirm handover before reports become Returned. Admin cannot confirm for a participant; dispute resolution requires an audited reason. Closed claims cannot send messages. Hidden reports preserve existing conversations but pause new claims and handover.
- Cloud pages fetch bounded server pages and exact counts rather than a 500-row snapshot. Smart Matching ranks the current compatible candidate page. Claims, recipient notifications and the active conversation subscribe to Supabase Realtime with authorized reads and periodic reconciliation. Actual WebSocket delivery and concurrent transactions still require live testing.
- Admin CSV exports omit private contact data and neutralize spreadsheet formulas. Hidden report photos may remain reachable by previously shared public URLs.
- University domain validation is specific to SEU. Update both SQL and TypeScript validation before adapting the project for another institution.

Before a public Cloud launch, request FINAL AUDIT and complete `SECURITY_TEST_CHECKLIST.md`, including real email delivery, separate-user/device checks, production build, deployed cache/headers and backup/restore verification. SMTP/abuse limits, monitoring and retention remain operational setup work.
